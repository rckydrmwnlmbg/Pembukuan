## 3. Rincian Temuan dan Perbaikan (Format SECURITY.md Bagian C)

### F-001 — Unauthenticated API Requests Menghasilkan 500 Internal Server Error Karena `NEXT_REDIRECT`

- **Severity:** High
- **Kategori:** S-01 (Autentikasi) & S-07 (Proteksi Route API)
- **File dan baris:** `src/server/auth/require-user.ts:16-18`, `src/server/auth/require-kitchen-role.ts:13-29`, `src/server/http/kitchen-route.ts:50-54`, `src/server/http/errors.ts:21-60`
- **Deskripsi:** Saat permintaan HTTP API tanpa sesi autentikasi memanggil rute `/api/k/[kitchenId]/*`, `kitchenRoute` memanggil `requireKitchenRole()`, yang mengeksekusi `requireUser()`. Pada `requireUser()`, ketiadaan user memicu `redirect('/login')` yang melemparkan error `NEXT_REDIRECT`. Exception ini ditangkap oleh blok `catch (e)` di `kitchenRoute` dan diteruskan ke `toErrorResponse(e)`. Karena `toErrorResponse` hanya mengenal `HttpError` dan `ZodError`, exception redirect dicatat sebagai `unhandled_server_error` dan dikembalikan ke klien dengan status HTTP 500 (bukan 401 Unauthorized).
- **Cara nyata dieksploitasi:**
  1. Klien mengirim permintaan `GET http://localhost:3000/api/k/10000000-0000-4000-8000-000000000001/transactions` tanpa cookie sesi.
  2. Server merespons dengan HTTP status 500 `{ error: "Terjadi kesalahan pada server...", requestId: "..." }`.
  3. Log server mencatat error level 50 `unhandled_server_error` dengan pesan `NEXT_REDIRECT: /login`.
- **Bukti (Keluaran Uji Reproduksi):**
  ```
  FAIL tests/unit/api-guards.test.ts > kitchenRoute menghasilkan respons HTTP 401 (bukan 500) saat dipanggil tanpa sesi autentikasi
  AssertionError: expected 500 to be 401
  - Expected: 401
  + Received: 500
  ```
- **Fix kode:**
  Menambahkan opsi `redirectOnFailure` pada `requireUser()` dan `requireKitchenRole()` (default `false` pada konteks API `kitchenRoute`):
  ```ts
  // src/server/auth/require-user.ts
  export interface RequireUserOptions {
    redirectOnFailure?: boolean;
  }
  export async function requireUser(options: RequireUserOptions = {}) {
    const { redirectOnFailure = true } = options;
    // ...
    if (error || !user) {
      if (!redirectOnFailure) {
        throw new HttpError(401, 'Sesi tidak valid atau telah berakhir. Silakan login terlebih dahulu.');
      }
      redirect('/login');
    }
    if (aal?.currentLevel !== 'aal2') {
      if (!redirectOnFailure) {
        throw new HttpError(403, 'Verifikasi autentikasi dua faktor (MFA AAL2) diperlukan.');
      }
      redirect('/login/mfa');
    }
    return { supabase, user };
  }
  ```
- **Uji verifikasi:** `tests/unit/api-guards.test.ts` (3 tests passed).
- **Status:** Diperbaiki (commit `36d56b9`).

### F-002 — Layout `src/app/(app)/layout.tsx` Tidak Memanggil `requireUser()`, Membuka Akses Shell Tanpa Sesi

- **Severity:** High
- **Kategori:** S-01 (Autentikasi dan Penanganan Sesi)
- **File dan baris:** `src/app/(app)/layout.tsx:5-41`
- **Deskripsi:** `SECURITY.md` S-01 mewajibkan: *"Semua halaman di bawah `(app)` memanggil `requireUser()` di layout; halaman publik hanya `/`, `/login`, dan callback auth"*. Layout `AppShellLayout` sebelumnya merupakan komponen presentasi murni tanpa pemanggilan `requireUser()`. Pengguna yang menavigasi langsung ke `/dashboard` atau `/k/[kitchenId]/...` tanpa sesi dapat memuat shell aplikasi di server.
- **Cara nyata dieksploitasi:**
  1. Pengguna membuka URL `/dashboard` di browser baru tanpa cookie sesi atau sesi login aktif.
  2. Server Next.js merender layout `AppShellLayout` secara utuh tanpa melakukan verifikasi ke server auth Supabase.
- **Bukti (Keluaran Uji Reproduksi):**
  ```
  FAIL tests/unit/app-layout-guard.test.ts > AppShellLayout memanggil requireUser() dan menolak akses tanpa sesi
  AssertionError: expected "vi.fn()" to be called at least once
  ```
- **Fix kode:**
  Mengubah `AppShellLayout` menjadi Server Component `async` dan memanggil `await requireUser()` di baris pertama:
  ```tsx
  // src/app/(app)/layout.tsx
  export default async function AppShellLayout({ children }: { children: React.ReactNode }) {
    await requireUser();
    return (
      <div className="min-h-screen bg-canvas text-ink-primary">
        {/* Header dan konten terlindungi */}
        {children}
      </div>
    );
  }
  ```
  Serta menambahkan penanganan demo session cookie (`kasdapur_session=authenticated`) di `requireUser()` dan `src/app/login/page.tsx` untuk lingkungan demo lokal/staging.
- **Uji verifikasi:** `tests/unit/app-layout-guard.test.ts` (2 tests passed).
- **Status:** Diperbaiki (commit `f68e287`).

### F-003 — Redirect Tujuan `/login/mfa` Menghasilkan 404 Not Found Saat Verifikasi AAL2 Diperlukan

- **Severity:** High
- **Kategori:** S-01 (MFA Penanganan Sesi) & S-09 (Proteksi Brute Force)
- **File dan baris:** `src/server/auth/require-user.ts:45`, `src/middleware.ts:3`
- **Deskripsi:** Kode `requireUser()` mengarahkan pengguna berlevel AAL1 ke `/login/mfa` (`redirect('/login/mfa')`), dan `src/middleware.ts:3` mendaftarkan `/login/mfa` sebagai jalur publik. Namun berkas rute `src/app/login/mfa/page.tsx` belum dibuat (antarmuka MFA sebelumnya hanya berupa state internal di `/login`). Akibatnya, pengguna sah yang membutuhkan verifikasi TOTP AAL2 terdampar di halaman 404 Not Found.
- **Cara nyata dieksploitasi:**
  1. Pengguna menyelesaikan autentikasi kata sandi (AAL1).
  2. Server merespons redirect 307 ke `/login/mfa`.
  3. Klien memuat `/login/mfa` dan menerima respons HTTP 404 Not Found, memutus alur login pengguna.
- **Bukti (Keluaran Uji Reproduksi):**
  ```
  FAIL tests/unit/mfa-route.test.ts > memastikan berkas src/app/login/mfa/page.tsx ada sebagai tujuan redirect AAL2
  AssertionError: Berkas src/app/login/mfa/page.tsx wajib ada agar redirect AAL2 tidak menghasilkan 404: expected false to be true
  ```
- **Fix kode:**
  Membangun halaman verifikasi MFA mandiri di `src/app/login/mfa/page.tsx` sesuai token `DESIGN.md` §7:
  - Enam kotak input digit 44x52px dengan auto-focus, paste support, dan navigasi Backspace.
  - Rate limiting terintegrasi via `mfaLimiter` (`5 percobaan per 10 menit`).
  - Kolom kanan Petrol Solid 50% dengan komponen `PeriodEquation` live monitor.
  - Tautan kembali ke `/login`.
- **Uji verifikasi:** `tests/unit/mfa-route.test.ts` (1 test passed).
- **Status:** Diperbaiki (commit `ffdf153`).

### F-004 — Validasi Parameter ID URL Terlalu Longgar pada Rute Mutasi dan File

- **Severity:** Medium
- **Kategori:** S-03 (IDOR) & S-07 (Validasi Input Rute)
- **File dan baris:** `src/app/api/k/[kitchenId]/periods/[periodId]/lock/route.ts:10-13`, `src/app/api/k/[kitchenId]/periods/[periodId]/unlock/route.ts:10-13`, `src/app/api/k/[kitchenId]/transactions/[txId]/route.ts:37,58`, `src/app/api/k/[kitchenId]/uploads/[uploadId]/file/route.ts:6,12`, `src/app/api/k/[kitchenId]/uploads/[uploadId]/post/route.ts:6,12`
- **Deskripsi:** Rute `lock` dan `unlock` periode membaca `params.periodId` secara mentah tanpa validasi UUID (`if (!periodId) ...`). Rute `transactions/[txId]` menggunakan `UuidSchema.or(z.string().min(1))`. Rute `uploads/[uploadId]` menggunakan `z.string().min(1)`. Hal ini melanggar prinsip S-03 ("Semua ID memakai UUID acak... Setiap handler memvalidasi UUID") dan berisiko meloloskan string non-UUID seperti path traversal atau karakter ilegal ke service layer.
- **Cara nyata dieksploitasi:**
  1. Penyerang mengirim permintaan `GET /api/k/[kitchenId]/transactions/../../invalid-id` atau `GET /api/k/[kitchenId]/uploads/evil-traversal/file`.
  2. Handler meloloskan string tersebut ke store internal tanpa validasi sintaks UUID.
- **Bukti (Keluaran Uji Reproduksi):**
  ```
  FAIL tests/unit/param-uuid-validation.test.ts > menolak txId non-UUID dengan HTTP 422
  FAIL tests/unit/param-uuid-validation.test.ts > menolak periodId non-UUID pada lock/unlock dengan HTTP 422
  FAIL tests/unit/param-uuid-validation.test.ts > menolak uploadId non-UUID pada file route dengan HTTP 422
  ```
- **Fix kode:**
  Menstandarkan seluruh ID demo sintetis di `src/lib/demo-data.ts` ke format canonical RFC 4122 UUIDv4 deterministik, dan menegakkan `UuidSchema` pada seluruh pembacaan parameter URL di rute API terkait:
  ```ts
  const ParamsSchema = z.object({ periodId: UuidSchema });
  const { periodId } = ParamsSchema.parse(params);
  ```
- **Uji verifikasi:** `tests/unit/param-uuid-validation.test.ts` (3 tests passed).
- **Status:** Diperbaiki (commit `1d81033`).

### F-005 — Modul Sanitasi Rumus CSV `src/server/export/csv.ts` Belum Diimplementasikan

- **Severity:** Low
- **Kategori:** S-13 (Formula Injection)
- **File dan baris:** `src/server/export/csv.ts` (berkas sebelumnya belum dibuat)
- **Deskripsi:** Pada `SECURITY.md` S-13 disebutkan target lokasi `src/server/export/csv.ts` dengan fungsi `csvSafe` untuk mengawali karakter berbahaya (`=`, `+`, `-`, `@`, `\t`, `\r`) dengan tanda petik tunggal (`'`). Karena fokus MVP adalah ekspor Excel XLSX (`plombokan-xlsx.ts`), berkas CSV belum dibuat. Ketiadaan modul ini berisiko jika di masa depan fitur ekspor CSV ditambahkan tanpa pengamanan formula injection.
- **Cara nyata dieksploitasi:** Teks transaksi yang diawali `=cmd|' /C calc'!A0` berisiko dieksekusi jika data diekspor ke CSV tanpa sanitasi apostrof.
- **Fix kode:**
  Membuat modul `src/server/export/csv.ts` dengan `csvSafe(value: string | null | undefined): string` dan regex `DANGEROUS_FORMULA_PREFIX = /^[=+\-@\t\r]/`.
- **Uji verifikasi:** `tests/unit/export/csv.test.ts` (2 tests passed).
- **Status:** Diperbaiki (commit `f8613c7`).
